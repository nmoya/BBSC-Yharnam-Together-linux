# Native Linux / NixOS co-op

This checkout's `bbport` builds a native Linux executable and statically links the co-op client
(`bbnet`) into `libbbgpu.so`. It does **not** need Wine, Proton or the Windows launcher. The game
assets must be supplied by the player; no assets are included here. Co-op expects Bloodborne
**01.09**. The EU edition CUSA03173 has the most testing.

## Build in a Nix shell

Use a nixpkgs with Qt 6.8 or newer (the current nixpkgs-unstable provides Qt 6.11). No global
installation or channel change is required. If your default `<nixpkgs>` is older, pass a local
nixpkgs checkout to `nix-shell` with `--arg pkgs 'import /path/to/nixpkgs-unstable {}'`.

```sh
git submodule update --init bbport/gpu/third_party/fsr-vulkan \
  bbport/gpu/third_party/imgui bbport/gpu/third_party/magic_enum \
  bbport/gpu/third_party/miniz bbport/gpu/third_party/xbyak \
  bbport/third_party/LibAtrac9 server/externals/protobuf
nix-shell shell.nix
BB_LTO=OFF BB_PGO=off bash bbport/build.sh
```

The root `shell.nix` includes `bbport/shell.nix` (GCC, CMake, Ninja, pkg-config, Python,
Vulkan, SDL3, JACK, FFmpeg, Boost, fmt, shader tools, protobuf, OpenSSL, zlib, miniupnpc,
the GPU's header libraries and X11/Wayland/ALSA), plus Qt 6 Core, Network, Sql, Concurrent
and HttpServer for the server. `build.sh` refreshes a stale CMake configuration when the Nix
compiler, SDL or protobuf path changes, without deleting compiled objects. The FSR submodule
gets the port's tracked patches applied by `build.sh` (it will appear modified in `git status`).
If nixpkgs' Vulkan headers do not define the optional VALVE mixed-float-dot-product extension,
the FSR 4.1.1 optimization using that extension is unavailable; ordinary rendering and co-op
do not depend on it.

## Join a friend's server (no local server needed)

From the repository root, inside `nix-shell shell.nix`:

```sh
python3 bbport/scripts/linux_coop.py \
  --game-dir /home/nmoya/Projects/bbport/game/Bloodborne/game \
  --server FRIEND_IPV4_OR_DNS \
  --data-dir "$PWD/local-data/client"
```

Until the generated party HUD's blinking placeholder elements are fixed, prepend
`BB_PARTY_HUD=0` to the client command. This leaves the co-op connection enabled but hides the
in-game party HUD. The native co-op path uses a fixed **60 FPS** for all players.

The script runs `bbport/run.sh` (which prepares/links the game and builds the native client).
It uses UDP port **31314** for the encrypted co-op link; supply `--server HOST:PORT` if your
friend changed that port. It points the game's HTTP backend at `http://HOST:20443` and its
WebAPI at `http://HOST:31315`; the friend must expose 31314/udp, 31315/tcp and 20443/tcp to you.
No `seamlesshunt.com` service is used. The server handles the game's backend and multiplayer
protocol; a separate Python game server is not needed.

With the command above, generated files live in this repository's **Git-ignored**
`local-data/client/` (`~/.local/share/yharnam-together/` is the script's default without
`--data-dir`): `user/coop-linux.json` contains a private per-server ID
and secret (mode 0600), `user/host_overrides.yharnam.json` maps Bloodborne's original server
to the friend's host, and `coop-mods/yharnam-coop-events/` contains event patches derived from your
own game files. The ROM is **not** moved, patched in place or duplicated. The script only
regenerates missing events; if the game files change, move the old generated event layer aside
and run it again. To prepare and check configuration without launching, add `--prepare-only`.

On first connection the game learns the host's public link key; the script stores the game's
confirmed key after the process exits. For stronger first-connection protection, ask the host
for the key (shown in the server log; `shadnet --admin key` on hosted servers) and pass
`--server-key HEX_KEY` before connecting. If a later key differs, the script refuses to replace
the pinned key. Your friend must run a compatible game/server release and protocol; differing
revisions, events and patches produce warnings to the players rather than protocol refusals.
An address change that changes the HTTP redirect requires `--replace-overrides`, and only a
file marked as generated by this script may be replaced. An existing
`user/host_overrides.custom.json` wins and is never modified.

When moving your game files later, update `--game-dir`; keep the data directory if you want
the same account and saves. Never share `coop-linux.json` or put secrets into run scripts.

## Host locally (optional)

The dedicated server is separate from the game. Inside `nix-shell shell.nix`:

```sh
cmake -S server -B server/build-linux -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build server/build-linux --target shadnet -j 2
mkdir -p "$PWD/local-data/server"
SHADNET_HOME="$PWD/local-data/server" server/build-linux/shadnet
```

On first run the server creates `shadnet.cfg` in `SHADNET_HOME`; stop it to edit the config,
then restart with the same command. Set `Host` to a reachable
interface (for all interfaces, `Host=0.0.0.0`; default `127.0.0.1` is local-only),
`BloodborneSeamlessCoop=true`, and leave `BloodborneBackend=true`,
`MakeAccountsAtSignIn=true` and `TcpLocalOnly=true`. Forward 31314/udp, 31315/tcp and
20443/tcp, **not** 31313/tcp. Keep the generated `link_key.bin`: losing it changes the server's
identity and breaks clients' key pins. If running behind a VPN, use its reachable IPv4 address;
only the host needs to run the server. See `server/hosting/README.md` for firewall and data
layout. Do not expose the management socket or database publicly.
See the root README for a safe copy of an older save into `local-data/client/user/savedata/`;
do not confuse the game's reported title ID with the title ID its save-data service mounts.

## Validation and limits

The event generator and CLI can be checked independently with `--prepare-only` and
`python3 -m unittest discover -s bbport/tests -p 'test_linux_coop.py'` in the Nix shell.
`bash bbport/build.sh --test` runs the port's C tests; server tests can be configured with
`-DBUILD_TESTING=ON` and run using `ctest --test-dir server/build-linux --output-on-failure`.
On the current NixOS toolchain the older port `pad-test` asserts on raw touchpad input (the
runtime now reserves the touchpad for the map and pings), and `runtime-test` assumes the host
allocator gives a thread-local pointer below 1 TiB. These are test failures, not successful
co-op validation; `file-mods-test` and `content-test` can be run independently.
In a local smoke test, the native game signed in to the local `shadnet` server, received the
encrypted UDP link welcome, made HTTP calls to its backend (including a `200` response), mounted
save data and continued running at about 60 FPS until the test timer stopped it after 50 seconds.
The earlier startup crash was a patch write to an RX game-code page: `bbgpu_init` had installed a
code hook on the same page before `apply_patches` wrote to it. The loader now reopens executable
patch pages before writing and sets their final segment protection after all hooks are installed.
This automated smoke test does not prove that two people can play together. In this
game build, the save-data service mounts title ID `CUSA00207` despite `param.sfo` reporting
`CUSA03173`; check the actual `user/savedata/1/` path when importing a save, and keep the source
save separate from the test profile. Consult `user/log/shad_log.txt` under your data directory
for connection diagnostics.
With a copy of the older `CUSA00207/SPRJ0005` save in that isolated profile, the next launch
mounted it as an existing read-only save. A subsequent interactive run reached the player's
character in the game. Disabling the generated party HUD (`BB_PARTY_HUD=0`) stopped its blinking
placeholder icons and text. Do not point the script directly at an original save directory while
testing.
The only proof of Linux-to-Windows co-op is a real join against your friend's server with a
compatible Windows build; compilation or local tests alone do not establish this.
